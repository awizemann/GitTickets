## Description

Turn the release ordering that keeps getting rediscovered into a written runbook, so it does not depend on whoever is driving remembering it.

The v1.1.0 failure (announced in README and CHANGELOG but not tagged, so from: "1.1.0" failed SPM resolution outright and forced ShabuBox onto 1.0.0) is the case to design against. v2.0.0 and v2.1.0 both got it right by following the same unwritten sequence.

## Plan

Write to documents/ (agent artifacts) or docs/ if it is project-owned documentation — decide which, since a release runbook is arguably the project's own.

Cover at minimum:

1. The ordering and WHY: merge, push, wait for CI green, only then tag, then prove the tag. Tag annotations carry measured facts, never intentions.
2. Proving a tag: resolve from: "<version>" from the PUBLIC remote with a cold SPM cache in a throwaway consumer, then build AND run it. This single check would have caught v1.1.0 instantly.
3. The README-claims-released-before-tag-exists window, and that it must be closed in the same session rather than left for a later one.
4. A pre-tag checklist: version metadata bumped, CHANGELOG entry with working link refs, no claim asserted that was not measured.
5. What to do when a tag is wrong — and note that v1.1.0 was backfilled on 2026-07-25, so the repair path exists and should be documented.
6. Relay templates version independently of the SDK; say how that interacts.
