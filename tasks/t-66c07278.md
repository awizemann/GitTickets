## Description

GitTicketsView holds screenshot state, renders its thumbnail, offers Remove, and passes it to submit — but nothing ever assigns it a non-nil value, and there is no "Add Screenshot" affordance. ScreenshotCapture.capture() is public and works for hosts with their own UI, so this is an unimplemented built-in-form affordance rather than dead code. Needs a product decision, not a rush fix. Found during v2.1.0 P3.

## Plan

GROUNDED EVIDENCE (verified 2026-07-26 against v2.0.0 and release/v2.1.0):
- Sources/GitTickets/UI/SwiftUI/GitTicketsView.swift:59 declares `@State private var screenshot: Data?`. It is READ at :169 (hasScreenshot:) and :289 (passed to submit), and SET TO NIL at :198 (onRemove). It is never assigned a non-nil value anywhere.
- grep for `ScreenshotCapture` across Sources/ outside its own directory returns NOTHING. platformCapture() is called only from ScreenshotCapture.swift:50.
- The form's only Buttons are Cancel and an alert OK. There is no capture trigger.
- CONTRAST: attachments ARE fully wired — .fileImporter at GitTicketsView.swift:115, appended at :271. So the attachment path works and the new v2.1.0 preview sheet serves a live path.
- ScreenshotCapture is PUBLIC (`public enum ScreenshotCapture`, `public static func capture()`), and its doc explicitly supports hosts with their own UI: "Public so hosts that present their own UI ... can capture a screenshot. Pass the returned Data as Report/screenshot."
- But the SAME doc comment implies the built-in form does it: "Capture is initiated only on direct user action (e.g. tapping 'Add Screenshot' in the form)" and "the caller (form view) surfaces the failure inline and allows submission without a screenshot."

So: the public API is functional; the built-in-form affordance the docs describe does not exist. The doc comment is currently misleading about the built-in form.

WHY THIS WAS NOT FIXED IN v2.1.0: it is outside the six ShabuBox asks, and adding it is a genuine product decision rather than a mechanical gap-fill. On macOS, capture requires Screen Recording (TCC) permission, and prompting a privacy-first document vault's users for full-screen recording access is a significant ask that could read as alarming in exactly the app where trust matters most. ScreenshotCapture's own doc already offers the alternative: "Hosts that don't want to ask for that permission can use an NSOpenPanel for an image file instead — the result lands in the same Report/screenshot / Report/attachments slots." Since the form already has a fileImporter for attachments, image-file attachment already covers most of the need without any permission prompt.

OPTIONS FOR ALAN:
(a) Wire an "Add Screenshot" button in the built-in form calling ScreenshotCapture.capture(), surfacing permission-denied inline. Delivers what the docs claim; triggers a TCC prompt.
(b) Leave the form as-is and CORRECT THE DOC COMMENT so it stops implying a built-in affordance — cheapest, and arguably the honest choice given the attachment importer already exists.
(c) Add it behind a policy flag, default off, so privacy-sensitive adopters never trigger the prompt.
Recommend (b) at minimum — an inaccurate doc comment is the same class of defect as v1.1.0's false toolchain claim, and it is nearly free to fix.

ALSO CORRECTS A PRIOR HAND-OFF ERROR: after v2.0.0 the orchestrator told Alan the highest-value manual check was "Report an Issue -> Add Screenshot", to validate the SCScreenshotManager rewrite. That affordance does not exist, so that instruction was not actionable. The v2.0.0 ScreenCaptureKit rewrite therefore remains UNEXERCISED AT RUNTIME unless a host calls ScreenshotCapture.capture() directly. Whoever picks this up should exercise capture() on macOS 14+ and confirm the success, permission-denied, and no-display paths — that is still outstanding from v2.0.0.
