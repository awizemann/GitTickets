## Description

macOS has NO refresh path for an open window. Measured 2026-07-26 against the real shipped view: `.refreshable` on a ScrollView is a complete no-op on macOS (it does not even propagate the refresh action into the environment), while on iOS it correctly installs a UIRefreshControl. Both GitTicketsMyIssuesView and IssueDetailView use ScrollView + .refreshable, so on macOS the only way to see a new issue or a new comment is to close and reopen the window.

Separately, MyIssuesPolicy.pollInterval is public API that nothing reads (Policies.swift:410) — no auto-refresh exists under any configuration.

## Plan

Blast radius: two view files, one new internal modifier, Policies doc, tests, CHANGELOG. No public API removed or changed in signature; pollInterval keeps its default of 0 so existing adopters see no behavior change.

1. New internal `refreshTriggers(pollInterval:action:)` ViewModifier in
   Sources/GitTickets/UI/SwiftUI/RefreshTriggers.swift. Shared by both views —
   reuse rather than duplicating three triggers twice. Deliberately internal:
   no new public surface to support.
   - Toolbar Refresh control. This is the ONLY affordance that works on macOS.
     Command-R shortcut, .help, explicit accessibility label.
   - Re-fetch when the scene becomes active, skipping the initial transition so
     it does not double-fetch against the existing .task.
   - Optional polling when pollInterval > 0, honoring task cancellation.
2. Apply to GitTicketsMyIssuesView and IssueDetailView. Keep the existing
   .refreshable — it genuinely works on iOS.
3. Wire pollInterval from GitTickets.configuration?.myIssues, same pattern the
   views already use for theme.
4. Fix the GitTicketsMyIssuesView.swift header comment: "the iOS .refreshable
   gesture on macOS too" is false.
5. Tests that exercise the triggers, not just their existence.
6. Verify with the retained harness that the macOS view gains an affordance.
