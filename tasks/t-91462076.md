## Description

ShabuBox ask #4 (nice-to-have). Let the user expand a pending attachment to full size in the compose form before submitting, so they can confirm what they are about to publish irreversibly to a public repo. Owns the compose-form attachment UI. Consult the design tier first.

## Plan

Base: release/v2.1.0 off v2.0.0 (a491180). Owns Sources/GitTickets/UI/SwiftUI/GitTicketsView.swift plus any new view file you add, and their tests. Parallel with P1 and P2. Do NOT touch Policies.swift, AuthMode.swift, IssueBodyBuilder.swift, or Diagnostics/.

CONSULT THE DESIGN TIER BEFORE WRITING UI. This repo has a design/ tier (searchable via the memophant MCP as project "gittickets-design", or grep design/). Find the existing conventions for surfaces, spacing, and the theme system, and follow them rather than inventing a look. The SDK is themeable via GitTicketsTheme — the preview must respect the adopter's theme, not hardcode colors.

CURRENT STATE: the compose form's attachment cell is 26pt (GitTicketsView.swift:135). For comparison, detail and My Issues thumbnails are 36-52pt (GitTicketsMyIssuesView.swift:195,222; IssueDetailComponents.swift:161,203) — those are OUT OF SCOPE, do not touch them. This is specifically about a PENDING (not yet submitted) attachment in the compose form.

WORK: click/tap a pending attachment to expand it to full size. Keep it simple and native — a sheet or popover showing the image at full size with an obvious dismiss. Both macOS and iOS must work (the package supports both; SwiftUI views here are shared). Respect Dynamic Type and don't break the form's existing layout when there are multiple attachments.

ACCESSIBILITY IS NOT OPTIONAL: the expand affordance needs a real accessibility label and must be reachable by keyboard on macOS and VoiceOver on both platforms. A tap-only affordance with no label is a regression, not a feature.

SCOPE DISCIPLINE: this is the lowest-priority item in the release. If it grows past a self-contained view plus a small change to the cell, STOP and report rather than expanding. Do not refactor the surrounding form. Do not restyle the existing 26pt cell beyond making it activatable.

VERIFY: swift build 0 warnings; swift test all green; xcodebuild -scheme GitTickets -destination 'generic/platform=iOS Simulator' -skipPackagePluginValidation build must SUCCEED (this is shared iOS/macOS UI code — a macOS-only API slipping in is the likeliest failure). Note that the snapshot test suite skips on CI and its baselines are gitignored; if your change alters the rendering of GitTicketsView, existing local snapshot baselines will mismatch — say so explicitly rather than silently re-recording, and explain what visually changed. Then a fresh-eyes audit: does the affordance survive an attachment being removed while the preview is open?

*** SEPARATE, MORE IMPORTANT FINDING: THE BUILT-IN FORM CANNOT ADD A SCREENSHOT ***
Orchestrator-verified, precisely:
- ATTACHMENTS ARE REACHABLE: GitTicketsView.swift:115 has a .fileImporter and :271 appends ReportAttachment. So P3's preview serves a live path.
- SCREENSHOTS ARE NOT: `@State private var screenshot: Data?` (line 59) is read at :169 and :289 and set to nil at :198, but NEVER assigned a non-nil value. There is no capture call and no "Add Screenshot" button anywhere in the form — the only Buttons are Cancel and an alert OK. grep for ScreenshotCapture outside its own directory returns NOTHING.
- ScreenshotCapture.capture() IS public and DOES work for hosts presenting their own UI — its doc comment explicitly supports that ("Public so hosts that present their own UI ... can capture a screenshot. Pass the returned Data as Report/screenshot").
So this is NOT dead code. It is a working public API plus an unimplemented built-in-form affordance that the same doc comment implies exists ("Capture is initiated only on direct user action (e.g. tapping 'Add Screenshot' in the form)" and "the caller (form view) surfaces the failure inline").
CONSEQUENCE FOR THE v2.0.0 HAND-OFF, WHICH WAS WRONG: the orchestrator told Alan to validate the ScreenCaptureKit rewrite via "Report an Issue -> Add Screenshot". That affordance does not exist. Exercising it requires calling ScreenshotCapture.capture() directly. Tracked separately; NOT fixed here (adding it is a product decision — asking a privacy-first document vault's users for Screen Recording permission is significant, and the doc itself offers NSOpenPanel as the alternative).

DESIGN TIER WAS ACTUALLY CONSULTED (from design/design_handoff_gittickets_views_generic/README.md): native semantic surfaces via GTSurface.ground/card/hairline/subtleFill rather than an invented palette; radii from GitTicketsTheme.cornerRadius (+1 for cards); the 52pt icon tile + .headline + centred .footnote ~300pt pattern borrowed from IssueStateCard for the no-preview state; .regularMaterial bar with top hairline from the pinned ActionBar; monospaced caption for numeric meta; 4pt spacing grid; native text styles so Dynamic Type works. The sheet deliberately uses ZERO hardcoded colors and ZERO accent tinting — it exists to show the user's own pixels honestly, and the dismiss control must stay legible under any adopter accent.

AUDIT FIXES IN THE SECOND COMMIT (two fresh-eyes specialist reviews found real defects):
- The footer and VoiceOver label quoted the DOWNSAMPLED bitmap's dimensions — a 4000x3000 screenshot was described as 2048x1536. A falsehood about the published bytes, on the one screen whose entire purpose is verifying them. Now reads true source dimensions from image properties (header-only).
- Decode blocked the main actor, stalling presentation and VoiceOver and making the .decoding state unreachable. Now detached, with cancellation.
- A 200pt cell cap could truncate the destructive "Remove" label at accessibility text sizes. Removed.
- Done was ~34pt on iOS (under the 44pt minimum) for the ONLY way out of a modal; label/hint duplication; .help colliding with .accessibilityHint on macOS; unlabelled per-file Remove; x and · read aloud as "multiplication sign"/"middle dot".

NON-IMAGE DECISION: the importer admits only image UTTypes, so the real case is corrupt/truncated bytes. The control is never dead — it always opens the sheet, which shows "No preview available", names the file, and states plainly that it will still be attached exactly as it is. That is the fact the user actually needs before submitting.
